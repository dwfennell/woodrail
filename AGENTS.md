# Woodrail — notes for agents

A Brio-style wooden railway game: TypeScript, Three.js, Vite, Rapier physics. It runs on phones, so keep CPU and GPU cost in mind.

## Commands

- `npm run dev`: dev server
- `npm test`: unit tests (Vitest)
- `npm run typecheck`
- `npm run build`
- `npm run build:artifact`: a build to publish as a claude.ai Artifact (see `docs/artifact-builds.md`)
- `npm run build:itch`: a build for itch.io, zipped (`woodrail-itch.zip`); releases push it there (see `docs/itch-builds.md`)
- `/publish-to-itch`: the release skill: checks, the devlog post (`docs/devlogs/`), moving the `itch` branch (which ships to players: only when the user asks)
- `E2E_PROFILE=1 npm run e2e:<suite>`: where a suite's time goes, by its script's lines, per group (`scripts/e2e/lib/profile.mjs`). The speed levers (the test clock, moves a few to a frame, device scale 1, Battery saver): `scripts/e2e/lib/fast.mjs`, `docs/agents/e2e.md` "Speed"
- `npm run fuzz:long [-- --seeds 200 --seconds 1800]`: the long routing fuzz with every train invariant, sharded over the cores; for release points (about 30 game minutes a seed)
- `npm test` runs the routing cases too (`src/routing/cases/`, twice: off and with the dispatcher on, about 100 s on 4 cores; docs/agents/routing-cases.md): about 400 small layouts generated from track × signals × trains × placement × stops, each judged by an exhaustive search of what a perfect dispatcher could do (`cases/oracle.ts`) against what the game does. A case the game gets wrong today is listed in `cases/known.ts` and must go wrong just that way (and with the train dispatcher on, `cases-on-*.test.ts`, in `cases/known-on.ts`: `--on`; new games keep it off till that list is empty); a change that clears one turns it red: take it out (`node tools/cases-known.mjs [--on] <dir>`). `rm -rf .cases; CASES_OUT=.cases npx vitest run src/routing/cases/; node tools/cases-report.mjs .cases`: the table of every case into the doc
- `npm run balance:sweep [-- --from 0 --to 200 --jobs 4]`: the `BALANCE=1` play-through over a range of player seeds, each checked against the bands at 180 min; for balance changes and release points (about a minute of CPU a seed)
- `npm run shadow:report [-- --seeds 40 --seconds 600 --parts plain,signals,ring,maps]`: the reservation core in shadow (routing redesign step 2, `src/routing/shadow.ts`): the fuzz's seeds and the bug maps run with it on, and where it disagrees with today's guards, counted by kind (held-free, ran-unbooked, shared-points, green-unbooked, red-booked…). It holds nothing: test and script only
- `npm run jams [-- --check | --update] [--maps a.txt,b.txt --seconds 1800] [--seeds 3 --out a.json --against b.json]`: the jams bar (dispatcher spec, `docs/superpowers/specs/2026-11-18-dispatcher.md` §8 step 0): the reference maps (`src/play/bugmaps/reference/`: the user's ten and our own twelve, `own-*`) run as a player would (the dispatcher off unless `JAMS_DISPATCHER=1`, whatever a map's save says), each jam cleared as a player would (`src/play/jams.ts`): jams, stops, longest stand, first invariant broken, against main's numbers (`baseline.json`; `--check` fails on a map worse). `--seeds N`: each map N times, its trains set going a few seconds apart (`startsOf`; seed 1 is the map as saved), mean, min and max per map, `--against` a run `--out` wrote; judge a dispatcher rule on the means, as single runs swing ±150 stops on a map. The dispatcher-on default bar and "no new breaks" are judged against `baseline-off-seeds.json` (main with it off, 3 seeds: `--against` it; main already breaks greenHeld on some maps there). For routing changes (about 8 min on 4 cores, N× with seeds)
- `npm run own-maps`: our own reference maps (`own-NN-*.txt` beside the user's in `src/play/bugmaps/reference/`), built by `src/play/own-maps/` with the game's placement rules on an empty Sandbox table: single lines with short loops, a figure of eight, a terminus throat, a wye, double track, rings, one-way signals, depot yards, the user's hill pattern. Rebuilding changes their files: run `npm run jams -- --update` after. `OWN_MAPS_SVG=<dir>` writes a schematic of each. What each shows: `docs/superpowers/specs/evidence/2026-11-18-dispatcher/own-maps.md`
- `npm run wiki [-- --out dist/wiki]`: the public wiki, static pages made from the game's own tables (`src/wiki/`, spec `docs/superpowers/specs/2026-11-07-wiki-design.md`); the Pages deploy puts it at `/woodrail/wiki/`. A new research row, industry, good, engine, wagon or explainer gets a page by itself
- `npm run wiki:pictures`: after a build, the wiki's pictures of each industry, engine and wagon (`src/wiki/pictures/`), the tray's own pictures drawn by the game headless (about 1 min). The wiki test fails when one is missing: run it after adding one, and again when a model changes. The game links to the wiki from ☰, industry cards and research tickets (`src/ui/wiki-link.ts`)
- Towns in rows (spec `docs/superpowers/specs/2026-11-14-town-rows-design.md`): a town's buildings are joined rows on pavement tiles (`src/props/rows.ts`; models `tools/blender/bldg_rows.py` into `public/models/rows.glb`: houses and shops that stack storeys, and the landmarks and civic places, each made for its lot of 1, 2 or 2×2 squares: `ROW_CIVIC`), and rows fill before the town spreads (`growTown`'s `rows`). A town from an older save is dressed in rows on load (`dressInRows`); the old `bldg-*` models stay in the catalogue. `npm run e2e:town-shape` and `e2e:town-drag` check what rows are for (every row house fronts a street, four in five touch a neighbour, a moved house takes its tile). `node tools/shots/town-rows.mjs [<out>]`: Larkfield at each level; `node tools/shots/row-models.mjs [<out>]`: each row model alone; `node tools/perf/town-triangles.mjs`: what a town's buildings cost to draw at each level
- `node tools/shots/train-models.mjs [<out>] [--only=engine,passenger]`: every engine and wagon alone beside a row house, with its size and triangles; `node tools/shots/yard-buildings.mjs [<out>] [--ids=bldg-school,grand-cathedral-4,…]`: the railway's yard buildings the same way, or any catalogue models by id. For judging a model change, before and after. The train build stops if a part comes out with wild coordinates (Blender's arc-mitred bevel over exact booleans, about one run in two: give that box `miter="MITER_SHARP"`, `tools/blender/toy.py`)
- `npm run bench:tick`: the sim + economy tick's cost (µs a tick) on each bug map (`src/play/bugmaps/*.txt`), headless, a plain Node bundle (`bench/tick.bench.ts`; `TICK_MAP=<part of a name>`, `TICK_SECONDS=120`). For a change to the sim, sections or router: before and after
- `npm run replay -- <file>`: replay a "Copy map for a bug report" text headless with the train invariants on, and print the first break (`src/play/bugmap.ts`)
- `npm run feedback -- <id or map link>`: fetch a "Report a bug or give feedback" report's map into a file for `npm run replay` (`--list` with `ADMIN_KEY` lists the latest; see `docs/feedback.md`)
- `npm run snapshots [-- <device id>]`: the latest railway snapshots from players who share them, or one device's into files for `npm run replay` (needs `ADMIN_KEY`; see `docs/stats.md`)
- `npm run activity`: the Woodrail Activity dashboard's numbers (play stats, feedback, snapshots, GitHub) into `activity-out/`, keys from 1Password by `op run`; itch's by hand (see `docs/activity.md`)
- `npm run e2e:affected [-- <base-ref>] [--run]`: the e2e suites (and groups) a branch's changes may affect, against origin/main by default; `--run` runs them. touch and click are picked by group (a smoke set for an unmapped path); `--nightly` runs them whole, a daily job. The map is `RULES` in `scripts/e2e/affected.mjs`: add a rule for a new module (see `docs/agents/e2e.md`). A file whose diff is only comments maps to no suite; only prose strings or CSS paint, to the suites that refer to those words or classes plus a 1.5-min smoke (`scripts/e2e/lib/diff-kind.mjs`)
- `/check`: what to run before handing a branch over for landing, by tier (copy, UI, rendering, sim/routing/economy, wide), and how to report it (`.claude/skills/check/SKILL.md`)
- Every e2e suite: `npm run e2e:<suite> -- --list` prints its groups; `E2E_ONLY=<group,…>` runs only those; a killed or timed-out run, run again on the same code, skips the groups that already passed (`group X: cached pass`, counted in the last line; `E2E_RESUME=0` runs all); `E2E_SHARD=i/n` runs a slice. Checkpoints in `.e2e-cache/` (`docs/agents/e2e.md`)
- `npm run perf [-- --maps fresh,late,sandbox,features --profile]`: the perf harness, after a build (see `docs/agents/perf.md`); `npm run perf:check`: it against `tools/perf/budgets.json` and then `perf:memory` (about 16 min; it includes the features map: each newer feature framed alone, paused, changed beside, and the crane at work)
- `npm run perf:memory [-- --suggest]`: the memory budget check, after a build (part of `perf:check`; about 4.5 min): the features map on a Pixel-10-like phone (mobile tier) and a desktop page (high tier): GPU bytes by the game's tally (geometry, textures, render targets, canvas), the JS heap and ArrayBuffers after GC, geometry and texture counts, and growth over rebuild cycles, against `tools/perf/memory-budgets.json`

## Performance: don't recompute what hasn't changed

The game should cost close to nothing when nothing is happening, and only pay for what changed when something does.

- **Render on change.** Draw a frame only when something visible changed: the camera moved, a train or animation is running, or `invalidate()` was called. Don't add work that runs every frame unconditionally.
- **Ambient animation draws only when it can be seen.** Motion that's there for looks (an industry's saw or axe, a boat, a road vehicle) asks for frames only while it's on screen *and* drawn big enough to see it move: test it with the frame's `AmbientEye` (`src/render/ambient.ts`: frustum and size in pixels, thresholds per kind in `AMBIENT_MIN_PX`), not with an object's `visible`. Zoomed out, it stands still and the map costs nothing. When ambient motion is all that moves, it's drawn at `AMBIENT_FRAME_MS` (15 a second); trains and the camera keep the full rate. New ambient motion follows the same rule.
- **Shadows** redraw only when a shadow caster moves (`moveShadows()`), something changes (`invalidate()`), or the shadow frustum refits. A camera move alone doesn't redraw them. A change that casts no shadow (draw's ghosts, a highlight, a trail) asks for a frame with `redraw()`, not `invalidate()`, and a flourish that moves no caster says `shadows: false`: the shadow pass is a second draw of everything in the sun's view (about a tenth of a frame on SwiftShader).
- **Rebuild incrementally.** When one thing changes, rebuild only the meshes, colliders or data it affects, not the whole map. For example, `HillCutsView` rebuilds only blocks whose cuts changed; the map-wide core and shadow mesh are rebuilt only when the set of cut blocks changes.
- **Key caches by their inputs.** Skip work when the inputs are the same as last time, such as a key built from the pose, or a signature of what's cut. Cache derived data per map (as `hillsOf(grid)` does).
- **Pointer moves are hot paths.** Code called on every pointer move while dragging (placement checks, previews) should be cheap and bounded. Time it, with a target of a few milliseconds on a phone.
- **Measure before and after** a performance change: idle CPU, frame time, the time of the operation itself. Note the numbers in the commit. `npm run perf` (tools/perf/run.mjs) measures three maps on a throttled phone-sized page (load, idle, paused, pan, tray drag, cards, autosave, draw calls, triangles, heap); `--profile` adds CPU profiles. How to read it: `docs/agents/perf.md`.
- **Budgets.** `npm run perf:check` (after a build, about 16 min; in the release gate) fails when a measure is over `tools/perf/budgets.json` (frames, draw calls, timings, bundle) or `tools/perf/memory-budgets.json` (memory: `perf:memory`). A change that rightly costs more updates the budgets in the same commit, saying why and with the numbers; one that saves a lot tightens them. `budgets.json`: `npm run perf:check -- --update` writes it from a run. `memory-budgets.json` changes only by hand: `npm run perf:memory -- --suggest` prints this run's values with their margins (6% for sizes, 5% for counts, 1 MB or 2 objects for leaks); copy in the ones you mean to change (`max`, and `measured`). Its margins sit above the run-to-run noise (three runs: `docs/agents/perf.md`, Memory budgets), so a failure there is a real change: don't raise a max to make it pass without finding what grew (the table names the measure; `node tools/perf/memory.mjs` and `heap-growth.mjs` say where).
- **Before adding per-frame work**, ask: does it need to run every tick, or on an event or a version change? `Game.frame` and `onFrame` run 30 times a second even when nothing is drawn, paused too. Does it allocate (arrays, closures, spreads, strings)? Does it write the DOM when nothing changed? Does it add draw calls or a new material (a new shader program to compile at load)?
- **Memory is a budget too** (a phone kills the tab at a few hundred MB). three keeps every vertex array after upload: mark static geometry that's only drawn with `gpuOnly` (`src/render/gpu-only.ts`; `pickable` if a raycast hits it), and don't keep two copies of a model. Measure with `node tools/perf/memory.mjs` (the JS heap's own count misses typed arrays; see `docs/agents/perf.md`, Memory); `npm run perf:memory` holds it to budgets.
- **Not while paused or idle.** A paused game, or one with nothing moving, should cost next to nothing: no placing objects that haven't moved, no re-uploading buffers that haven't changed, no saving what hasn't changed.

## Testing: check the player's path, end to end

A feature works only if a player can reach it and it pays off. (A restored old farm once shipped that couldn't farm: the play-through skipped the "Open a …" goals and the e2e stopped at the restore button.)

- **Every goal is reached by the player's path** in the play-through (`src/play/balance.test.ts`): through the actions a player takes (tray drops, card buttons, prices paid), not by writing state (`learned.add`, `coins =`, `piles[…] =`, placing depots directly). A goal that can't be is on an explicit allowlist with a reason, and a guard test fails when a goal is neither reached nor allowlisted.
- **Assert the payoff, not just the UI.** An e2e or test for a feature checks what it is for: an industry produces and its goods are carried, a goal ticks, a train delivers. Not only that a card opened or a button went away.
- **The harness uses the game's own rules.** Same footprints, prices and reach as `main.ts`. A harness-only shortcut must be named and commented, and never stands in for the player's path of the thing under test.
- **Every save in the repo loads and round-trips** (`src/persist/corpus.test.ts`, in `npm test`): the persist fixtures, the bug and reference maps, the report maps (`docs/agents/reports/*.txt`), and a save of every older version that still loads, each loaded with nothing clamped or dropped (`LoadReport`), saved, loaded and saved again the same. A feature that adds saved state adds a fixture at its maximum (as `save-maxima.test.ts` builds one), and a save version bump adds a save of the old version to `src/persist/fixtures/`.
- **Shortcuts in setup are fine** (learning research to get to a state quickly), but only for what isn't the thing being tested.

## Design skill

`.claude/skills/impeccable` (with helper agents in `.claude/agents/impeccable-*`) is the Impeccable design skill, vendored from github.com/pbakaus/impeccable. Use `/impeccable` (e.g. `critique`, `polish`, `clarify`, `adapt`) for HUD, card, menu and tray work. It is written for websites: keep the game's wooden-toy look and the phone limits above. Its launcher downloads a checksum-verified binary from the repo's GitHub releases on first run. Its hooks are not installed.
